# Guardians production deployment prompt

Copy the following prompt into a Codex session with this repository and the required account access. This is an evidence-based release process, not a guarantee that a deployment has no vulnerabilities.

```text
Take Guardians from its current checkout to a verified production release for Android, iOS, and web. Work in /Users/rivu/guardians/guardians-app. Implement and validate needed fixes, then carry the release through the authorized external steps. Do not stop at an audit or a passing build. Do not claim a platform is deployed until the deployed artifact is accessible and verified.

Read AGENTS.md, PRODUCTION.md, PRODUCTION_REVIEW.md, DEPLOY.md, supabase/README.md, and docs/release/*.md. Use the Expo overview skill and the relevant build/store, hosting, and update skills. Check the actual installed SDK and exact versioned Expo docs; this checkout currently uses SDK 57. Preserve existing app/store/project identifiers, visual identity, behavior, SECURITY DEFINER writes, PlatformMap, dialog helpers, and design tokens. Preserve user work. Treat historical docs and prior validation counts as history, not current evidence.

Scope and authorization:
- Prepare and test all three platforms. Confirm the actual production EAS, Supabase, hosting, and store projects before making external changes. If a release target is already established in this session, use it.
- Read-only checks and reversible repository fixes are authorized. Use existing account access; leave passwords, MFA, private keys, and billing decisions to the owner. Never ask for secrets in chat or expose them in outputs, logs, commits, artifacts, screenshots, or shell history.
- Prepare concrete changes and evidence before requesting any required approval. Obtain explicit approval for new charges, destructive data operations, or a public production rollout if not already authorized. TestFlight/internal testing approval does not imply public publication. Do not bypass tool approval requirements.
- No support contact or production web origin has been selected. Inspect existing owned domains. Propose a support/deletion page on the selected owned origin, with an owner-approved working contact channel and an actionable deletion request process. Implement the page after the contact details are provided. Do not invent contacts or fill EXPO_PUBLIC_SUPPORT_URL with a placeholder. Missing contact, domain, credentials, or required device evidence is a release blocker; continue independent preparation and report the exact missing input.

1. Establish the release baseline.
Record git branch/commit, worktree state, SDK/Node/EAS CLI versions, CI status, EAS project identity, Supabase project reference, hosting origin, store app identifiers, deployed versions, and enabled features. Use a staging backend distinct from production where possible. Do not copy production personal data to fixtures. Inspect current cloud state rather than assuming local .env is the production environment. Use test users for behavioral validation.

2. Validate and harden the implementation.
Run app/test typechecks, lint, formatting, Jest, Expo dependency compatibility/Doctor, dependency audit, all-platform Metro exports, browser smoke tests, Edge Function checks/tests, and local database pgTAP/security tests. Fix failures with focused changes and meaningful regression tests. Audit client bundle secrets, auth/cache isolation, input/file limits, RLS/Storage policies, RPC grants/search_path, ownership/status transitions, function authentication/CORS, moderation, abuse controls/rate limits, precise location access, and deletion of uploads plus related user data. Inspect SECURITY DEFINER authorization behavior with anonymous and multiple-user tests. Assess audit findings rather than blindly upgrading or suppressing them. Verify that optional AI/screening integrations are either configured and tested or explicitly disabled without bypassing adoption eligibility checks.

3. Configure production safely.
Verify EAS production variables: Supabase public URL and anon/publishable key, EAS_PROJECT_ID, EXPO_PUBLIC_SUPPORT_URL, restricted Maps keys, feature flags, and Sentry configuration when enabled. EXPO_PUBLIC_* is public even if marked secret in a dashboard. Never bundle service-role, provider, AI, webhook, or signing secrets. Use EAS environment commands supported by the installed CLI. Native source-map upload requires a secret SENTRY_AUTH_TOKEN when Sentry is enabled. Verify the resolved config without exposing keys; run release checks separately for android, ios, and web. Check app.config project ID and updates URL agree. Verify production/update environment consistency and fingerprint runtime compatibility.

4. Deploy the backend in the correct order.
Inspect linked migration history and actual hosted schema. Production has historically used timestamped migration records while local files use numeric names: do not blindly run supabase db push, reset a hosted database, or replay side-effect migrations. Build an explicit plan for only missing SQL and any history repairs, with backup/restore evidence and a staging rehearsal. Deploy the compatible send-push function BEFORE migration 0038. Verify current migrations through at least 0038 and include newer required migrations if present. Account for migration 0034 disabling legacy push registrations. Redeploy required Edge Functions while preserving their documented JWT/webhook authentication; do not globally disable auth as a workaround. Verify backend secrets without printing values. Run schema assertions and behavioral authorization checks against the deployed schema. Verify webhook authentication, retries/idempotency, provider failures, and alerting. Document forward fixes and restore procedures; do not blindly reverse destructive SQL.

5. Verify authentication and public pages.
Configure final Supabase Site URL, exact web/native callback allowlists, production SMTP and confirmation/reset templates. Refresh /auth/v1/settings but do not mistake it for verification of SMTP, credentials, or allowlists. Test actual signup, confirmation/resend, recovery, login/logout, account switching, cancellation, expired/replayed callbacks, and cold/warm deep links in installed builds and web. Test cross-device email links. Test Google/Apple only if enabled and intended for launch; verify consent publication and credential rotation. Verify privacy, terms, support, and deletion information anonymously at the final HTTPS origin. Ensure disclosures match actual processing and permissions. Confirm moderation coverage and real support delivery.

6. Verify native credentials and build artifacts.
Confirm signing, store membership/access, unique bundle/package identifiers, remote version counters, production AAB/IPA settings, APNs/FCM credentials, Android notification channel, and least required merged permissions. Verify Android Maps key restrictions for BOTH EAS upload/direct-install and Google Play app-signing SHA-1 certificates with com.guardians.app. If Google Maps is enabled on iOS, verify its bundle-ID restriction; otherwise verify Apple Maps. Confirm Maps API billing/quota. Build production candidates only after prerequisites pass. Record immutable build IDs, commit, runtime, version/build numbers, and build results. Test the exact candidate that will be submitted.

7. Test release candidates and deploy web.
Use physical iOS/Android release builds for signup/reset, session persistence, denied permissions, photo capture/upload, nearby map, claim/rescue/adoption, screening outcomes, comments, rewards, flag/block, push opt-in/out, notification cold launch, offline/retry, account switching, and account deletion with uploads. Verify private data never crosses accounts and public precise coordinates remain protected. If devices or testers are unavailable, mark acceptance blocked rather than treating mocks/simulators as equivalent.
For web use the established hosting provider; do not switch providers without reason. Export with production configuration enforcement and cleared Metro cache (npm run build:web:production). Inspect emitted JS for the intended backend and absence of fixture hosts, test keys, and privileged credentials without printing secrets. Verify HTTPS, routes/direct reload, OAuth callbacks, public legal/support pages, appropriate cache/security headers, real provider responses, and the live immutable asset after deployment. EAS Hosting alone does not deploy Supabase functions or schema.

8. Submit, stage, and verify distribution.
Configure Android submission credentials safely and use explicit tested build IDs rather than an ambiguous --latest. Current eas.json targets the Play internal track; keep that distinction clear. Set up iOS App Store Connect submission for the existing app using verified credentials/app ID; interactive configuration is valid if no static profile exists. Complete screenshots, descriptions, privacy/data-safety declarations, content rating, deletion/support URLs, permissions explanations, review access, and store testing requirements using current official rules. Verify TestFlight processing and tester access and Play track availability. Obtain any outstanding public-rollout approval only after a concrete tested candidate and evidence report are ready. Then perform staged public rollout and verify store availability separately from upload success.

9. Operate and document the release.
Verify a controlled diagnostic event and readable source maps without personal data, backend/push failure alerts, provider quotas/cost controls, backup restore readiness, moderation/support ownership, and thresholds for halting rollout. Document web rollback to an immutable prior deployment, compatible OTA recovery using the production environment/channel, new-binary recovery for native changes, and database forward-fix/restore constraints. Native changes require a new binary; never send an incompatible OTA.

Deliver:
- Implemented fixes and updated runbooks, with commits/PRs through the authorized repository workflow.
- A release evidence file containing commit, actual check results, migration/function deployment evidence, build/submission IDs, deployed URLs/versions, acceptance results, and rollback steps. Include no secrets or personal data.
- Per-platform status: prepared, built, tested, submitted, available to testers, or publicly live. Separately report backend and web status.
- A concise list of remaining blockers with the exact owner action required. Never label the release fully safe, secure, or complete solely because CI passed. Continue until all authorized and accessible work is complete, and state clearly what still cannot be verified.
```
